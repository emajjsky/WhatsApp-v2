# WhatsApp Agent 企业版 1.0.0 需求规格

> 状态：Draft（需求阶段）  
> 分支：`enterprise-1.0.0`  
> 基线：`Electron-desktop` 分支提交 `ddef906`  
> 日期：2026-09-29

## 1. 背景与目标

当前版本已经具备 Windows 桌面端 WhatsApp 连接、聊天处理、回复 Agent、Skill/话术、Provider 配置、采纳记录和云端鉴权能力，但数据和权限仍以“单个用户 + 本地数据库 + 全局管理员配置”为主。这个模型无法支撑公司客户、多个业务体系、多个团队和商业化交付，也无法让公司管理员看到成员的聊天与采纳数据。

企业版 1.0.0 不在 `main` 或 `Electron-desktop` 主线上直接改造，而是从 `enterprise-1.0.0` 分支开始，目标是建立可持续演进的多租户企业平台，同时保持第一批用户继续使用原主线版本进行验证。

企业版的核心边界是：

```text
软件提供方平台（Platform）
└── 公司租户（Organization）
    └── 业务体系 / 工作区（Workspace）
        └── 团队（Team）
            └── 团队成员（Member）
                └── 本地 WhatsApp 账号与设备（Desktop Data Plane）
```

企业版必须把“平台控制面”“公司/团队业务控制面”和“本地 WhatsApp 数据面”分开设计，不能继续把云端管理数据、本地聊天缓存和产品平台运维数据混成一个权限域。

## 2. 产品目标

### 2.1 必须达成

1. 支持平台、公司、业务体系/工作区、团队、成员五层组织边界。
2. 支持平台超级管理员、公司管理员、团队管理员/负责人、普通成员四类企业角色，并以权限范围而非单一 `admin` 字段决定可见内容。
3. 公司管理员可以查看本公司所有团队成员的聊天、Agent 运行、Skill/reference 命中、采纳和使用量数据；团队管理员只能查看本团队数据；普通成员默认只能查看自己的数据。
4. Provider、Model、Agent、Skill、reference 和配额支持平台级、公司级、团队级作用域，并明确继承、覆盖和编辑权限。
5. 本地继续负责 WhatsApp 实时连接和敏感会话资产；云端成为企业权限、配置、审计、统计和可选聊天归档的正式数据源。
6. 前端在登录后维护统一的公司/工作区/团队上下文，所有列表、接口、缓存和本地数据键都必须带作用域。
7. 所有同步、Agent、Skill、采纳和管理操作可审计、可追踪、可重试，且不因网络中断导致重复写入或越权读取。
8. 版本从 `1.0.0` 独立规划，具备企业授权、套餐/席位、灰度升级、签名安装包、数据库迁移和回滚策略。

### 2.2 明确不做

1. 不把所有客户的 WhatsApp 账号集中连接到服务器；本地 WhatsApp 会话仍是桌面数据面。
2. 不默认让软件提供方查看客户聊天正文、私有话术或业务资料。
3. 不允许团队管理员跨团队创建、编辑、删除公司管理员或平台管理员。
4. 不把当前 `admin@example.com` 的历史超级管理员逻辑直接扩展成企业组织权限；该账号只保留为平台初始超级管理员迁移入口。
5. 不在第一阶段把 PDF/Word 解析、复杂向量检索或全自动发消息和多租户基础模型混在一次迁移中；这些能力必须建立在作用域和审计基础上。
6. 不要求普通用户安装 Go、Node.js、Python、PostgreSQL 或 Docker；桌面安装包继续内置运行时。

## 3. 角色、组织与数据边界

### 3.1 平台层

平台超级管理员负责产品自身的控制面：

- 公司租户、套餐、订阅、席位和授权周期。
- 平台模型目录、全局可用 Provider 类型、公共 Agent/Skill 模板。
- 企业版安装包、最低支持版本、灰度范围、强制更新和 OTA。
- 平台级健康状态、用量聚合、错误指标和运维审计。
- 客户支持访问申请的审批、范围、过期时间和审计。

平台管理员默认不能直接查看客户聊天正文、私有 reference 原文、客户 API Key 或本地 WhatsApp 会话凭据。只有经过审批的临时支持访问才能读取指定范围的脱敏数据。

### 3.2 公司层

公司管理员负责本公司的业务控制面：

- 创建和管理本公司的工作区、团队和成员。
- 查看本公司全部成员的聊天归档、采纳数据、Agent 运行和使用统计，但必须服从公司内部的数据保留与脱敏策略。
- 管理公司级 Provider、Model 可用范围、Agent、Skill、reference、配额和默认策略。
- 将平台公共 Agent/Skill/Model 授权给工作区或团队，并设置公司级覆盖值。
- 不能查看其他公司数据，不能修改平台目录和其他公司的配置。

### 3.3 团队层

团队负责人/团队管理员负责一个团队：

- 查看本团队成员、账号、聊天、采纳、Agent 运行和使用量。
- 新增、邀请、停用本团队普通成员。
- 管理团队级 Provider、Agent、Skill、reference、话术规则和分配策略。
- 只能编辑自己有权限编辑的团队级资源；继承的公司/平台资源默认只读。
- 不能跨团队读取数据，不能创建公司管理员，不能删除公司或团队。

### 3.4 成员层

普通成员默认只能：

- 使用被分配到当前团队的 WhatsApp 账号。
- 查看自己的聊天、草稿、Agent 运行、Skill 命中和采纳记录。
- 使用团队允许的 Agent/Skill/Provider，不可查看 Provider API Key 和内部提示词。
- 不能修改公司/团队配置，不能查看其他成员的聊天正文。

### 3.5 数据分级

| 数据类别 | 默认归属 | 公司管理员 | 团队管理员 | 普通成员 | 平台管理员 |
| --- | --- | --- | --- | --- | --- |
| 账号、成员、团队关系 | 公司/团队 | 本公司 | 本团队 | 自己相关 | 元数据，平台运维需要时受控 |
| 聊天正文和附件 | 团队/公司策略 | 本公司范围 | 本团队范围 | 自己授权范围 | 默认不可见 |
| 采纳数据 | 产生该数据的团队 | 本公司 | 本团队 | 自己 | 仅聚合指标，正文受控 |
| Agent 运行 trace | 产生该运行的团队 | 本公司 | 本团队 | 自己 | 默认只看健康指标 |
| 私有 Skill/reference | 资源所属公司/团队 | 所属公司 | 所属团队 | 只读使用结果 | 默认不可见 |
| Provider 凭据 | 所属公司/团队 | 可管理元数据，不回显密钥 | 可管理团队凭据 | 不可见 | 平台托管凭据受控 |
| 计费、套餐、OTA | 平台/公司 | 公司订阅视图 | 不可见 | 不可见 | 全量 |

## 4. 功能需求

### 需求 1：组织与租户生命周期

**用户故事：** 作为平台管理员，我希望先创建公司、工作区和团队，再邀请成员，以便每个用户从第一次登录起就拥有明确的数据归属。

#### 验收标准

1. WHEN 平台管理员创建公司 THEN 系统 SHALL 同时生成公司唯一 ID、默认公司管理员邀请和审计事件。
2. WHEN 公司管理员创建工作区或团队 THEN 系统 SHALL 校验其只能在当前公司范围内操作。
3. WHEN 管理员邀请用户 THEN 系统 SHALL 要求选择公司、工作区、团队和角色，不允许创建无归属用户。
4. WHEN 用户接受邀请并登录 THEN 系统 SHALL 建立用户与公司、工作区、团队的成员关系，并返回可用上下文列表。
5. IF 用户属于多个团队 THEN 系统 SHALL 在进入工作台前要求选择当前工作区/团队，或恢复上次合法选择。
6. IF 用户被停用或移出团队 THEN 系统 SHALL 立即撤销该团队上下文下的访问能力，但不删除历史审计和业务记录。

### 需求 2：登录与桌面会话

**用户故事：** 作为企业成员，我希望使用手机号或邮箱登录，并在重新打开桌面客户端时恢复上次账号和工作区，而不是错误地进入平台超级管理员账号。

#### 验收标准

1. WHEN 用户注册或接受邀请 THEN 系统 SHALL 支持国家/地区选择、国际区号、手机号格式校验和邮箱校验。
2. WHEN 桌面客户端保存登录状态 THEN 系统 SHALL 按 `user_id + organization_id + workspace_id + team_id + device_id` 隔离本地会话缓存。
3. WHEN 用户选择“记住登录状态”或“记住密码” THEN 系统 SHALL 使用系统安全存储保存可撤销凭据，不得把明文密码写入 localStorage、普通配置文件或日志。
4. IF 本地存在多个合法账号 THEN 系统 SHALL 显示账号选择，不得默认回退到 `admin@example.com`。
5. IF 当前团队上下文失效 THEN 系统 SHALL 清除失效上下文并要求用户重新选择，不得静默切换到另一个用户或平台账号。

### 需求 3：权限与策略执行

**用户故事：** 作为公司或团队管理员，我希望系统按组织范围强制执行权限，而不是只在前端隐藏按钮。

#### 验收标准

1. WHEN 请求访问公司、团队、聊天、Agent、Skill、Provider、采纳或日志资源 THEN 服务端 SHALL 同时校验用户角色、组织关系、资源作用域和操作权限。
2. IF 用户修改请求中的 `organization_id`、`workspace_id` 或 `team_id` THEN 服务端 SHALL 以服务端会话和资源归属为准，拒绝越权范围切换。
3. WHEN 前端根据 capability 隐藏导航 THEN 服务端 SHALL 仍对所有 API 进行独立授权校验。
4. IF 公司管理员访问本公司数据 THEN 系统 SHALL 允许公司范围查询；IF 团队管理员访问数据 THEN 系统 SHALL 自动限制为当前团队；普通成员 SHALL 自动限制为自身授权范围。
5. WHEN 管理员新增成员 THEN 系统 SHALL 只能授予其不高于自身的组织级角色。
6. WHEN 删除、停用或移除成员 THEN 系统 SHALL 默认采用软删除/停用，保留聊天、采纳、审计和计费关联。

### 需求 4：Provider、Model、Agent、Skill 作用域

**用户故事：** 作为企业管理员，我希望公共模型能力可以复用，但每家公司和团队又能拥有独立的 Provider、Agent 和话术资料。

#### 验收标准

1. WHEN 创建 Provider、Model、Agent、Skill 或 reference THEN 系统 SHALL 要求资源作用域为平台、公司或团队之一，并记录创建者和所属组织。
2. WHEN 用户查看资源列表 THEN 系统 SHALL 展示资源来源、继承关系、是否可编辑、是否可复制和当前生效版本。
3. WHEN 团队使用公司或平台资源 THEN 系统 SHALL 允许按授权策略只读继承；团队覆盖必须创建明确的团队版本，不得隐式修改上级资源。
4. WHEN 删除或停用资源 THEN 系统 SHALL 检查引用关系、运行历史和数据保留要求，避免历史 Agent run 无法解释。
5. IF Provider 包含 API Key、Authorization 或私密 Endpoint THEN 系统 SHALL 仅在服务端加密保存，响应和日志不得回显完整凭据。
6. WHEN 回复 Agent 使用 Skill THEN 系统 SHALL 记录被选中的 Skill、reference、版本、召回结果和是否实际注入模型上下文。
7. WHEN 状态卡 Agent 运行 THEN 系统 SHALL 明确其只能把状态卡当作辅助信号，不能替代当前消息、聊天上下文和业务规则。

### 需求 5：本地聊天数据与云端企业数据同步

**用户故事：** 作为公司管理员，我希望看到成员的聊天和采纳数据；作为成员，我希望 WhatsApp 连接和敏感会话仍在本地运行。

#### 验收标准

1. WHEN 桌面端产生账号、聊天、消息、Agent run、采纳或审计事件 THEN 本地 SHALL 先写入本地数据库和幂等同步队列。
2. WHEN 网络可用 THEN 同步队列 SHALL 按事件 ID 上传到当前公司/工作区/团队对应的云端接口，并支持失败重试、退避和断点恢复。
3. IF 同一事件重复上传 THEN 云端 SHALL 使用 `event_id` 或等价幂等键只落库一次。
4. WHEN 公司或团队管理员查询数据 THEN 系统 SHALL 以云端已确认数据为准，并明确展示本地未同步数量和最后同步时间。
5. WHEN 公司配置为“仅元数据同步” THEN 系统 SHALL 不上传聊天正文和附件；当配置为“文本同步”或“完整归档”时，必须经过公司策略和用户告知。
6. IF 用户离线 THEN 桌面端 SHALL 继续支持已授权的本地聊天操作，但不得伪造云端已同步状态。
7. WHEN 本地数据同步失败并超过保留期限 THEN 系统 SHALL 产生可见告警，允许导出、重试或人工处理，不得静默丢弃。

### 需求 6：企业前端工作区上下文

**用户故事：** 作为多团队用户，我希望界面始终显示当前公司、工作区和团队，切换后所有数据和配置同步刷新。

#### 验收标准

1. WHEN 用户登录成功 THEN 前端 SHALL 初始化统一 `TenantContext`/`WorkspaceContext`，至少包含组织 ID、工作区 ID、团队 ID、角色、权限和 capability。
2. WHEN 用户切换工作区或团队 THEN 前端 SHALL 刷新账号、聊天、Agent、Skill、Provider、成员、采纳和日志数据，并清除不属于新范围的选中项。
3. WHEN 请求企业 API THEN 前端 SHALL 通过统一 API 客户端传递上下文和会话，不允许各页面自行拼接作用域参数。
4. WHEN 本地缓存聊天、草稿、筛选或最近账号 THEN 缓存键 SHALL 包含用户和组织层级，避免不同用户或团队串数据。
5. WHEN capability 不包含某个功能 THEN 前端 SHALL 隐藏导航和操作入口，并对直达路由显示明确的无权访问页面。
6. WHEN 公司管理员进入后台 THEN 系统 SHALL 提供公司范围、工作区范围和团队范围筛选；团队管理员 SHALL 不能选择其他团队。

### 需求 7：审计、运行日志与采纳

**用户故事：** 作为公司管理员，我希望知道 Agent、Skill、JEV/决策模型和话术 reference 是否真正被调用，并能追踪采纳结果。

#### 验收标准

1. WHEN Agent 生成回复、翻译、状态卡或决策结果 THEN 系统 SHALL 记录请求者、组织范围、账号、会话、Agent、Provider、模型、Skill、reference、耗时、结果状态和错误摘要。
2. WHEN 用户采纳、编辑、写回或发送回复 THEN 系统 SHALL 记录建议原文、用户编辑后的内容、最终动作和关联 Agent run。
3. WHEN 管理员查看日志 THEN 系统 SHALL 支持按公司、工作区、团队、成员、账号、Agent、Skill、Provider、模型、时间和结果状态筛选。
4. WHEN 平台管理员查看平台指标 THEN 系统 SHALL 默认只展示聚合数量、延迟、错误率、额度和健康状态，不展示客户正文。
5. WHEN 发生临时支持访问 THEN 系统 SHALL 记录审批人、访问人、范围、理由、开始时间、过期时间和所有读取行为。
6. WHEN 日志达到保留期限 THEN 系统 SHALL 按公司策略归档或删除，并保留不可篡改的摘要审计记录。

### 需求 8：套餐、席位与商业化

**用户故事：** 作为软件提供方，我希望按公司和团队提供可控的席位、模型调用量、Skill/reference、存储和日志能力。

#### 验收标准

1. WHEN 公司订阅套餐 THEN 系统 SHALL 记录套餐版本、生效期、席位上限、团队上限、Agent/JEV 调用额度、存储和日志保留期。
2. WHEN 公司创建成员或运行模型 THEN 系统 SHALL 检查对应配额，超限时提供明确的阻断或降级策略。
3. WHEN 平台发布公共模型、Agent 或 Skill THEN 系统 SHALL 支持按套餐、公司或团队授权。
4. WHEN 公司停用或到期 THEN 系统 SHALL 按策略限制新增操作，但保留数据导出、续费和管理员恢复入口。
5. WHEN 统计用量 THEN 系统 SHALL 使用幂等事件和明确的计量单位，避免本地重试造成重复计费。

### 需求 9：OTA、版本和发布

**用户故事：** 作为平台运维人员，我希望企业版可以安全灰度升级，不影响原主线用户，也不因迁移失败破坏本地聊天。

#### 验收标准

1. WHEN 发布企业版安装包 THEN 系统 SHALL 生成版本、渠道、适用组织/团队、最低支持版本、SHA-256、签名和发布日期。
2. WHEN 灰度发布 THEN 系统 SHALL 支持平台、公司、工作区和团队级范围，并记录已分发、已下载、已安装、失败和回滚状态。
3. WHEN 客户端升级前 THEN 系统 SHALL 备份本地数据库、校验安装包签名和兼容性，再执行迁移。
4. IF 数据库迁移或启动探针失败 THEN 客户端 SHALL 能回滚到上一个可启动版本，且不能删除原始聊天数据。
5. WHEN 企业版与云端 API/Agent Runner 交互 THEN 双方 SHALL 校验协议版本和最低客户端版本，避免新客户端调用旧接口产生静默错误。
6. WHEN 原 `main` / `Electron-desktop` 继续发布 THEN 企业版分支 SHALL 不改变其版本线、部署项目、数据库卷和用户数据。

## 5. 非功能需求

### 5.1 架构与代码质量

- Go API 继续负责业务服务、权限、数据访问和迁移；Handler、Service、Repository、Policy 分层。
- React 前端新增统一上下文和 capability 层，页面不得自行复制授权判断。
- Electron 只负责桌面壳、本地进程编排和安全存储，不把企业权限复制成前端信任逻辑。
- Agent Runner 只接收已授权、已脱敏、带作用域的运行请求；每次运行返回 trace ID。
- 新表和新 API 必须包含组织作用域、创建者、审计和幂等设计，不接受无归属的全局业务记录。

### 5.2 性能

- 登录后上下文初始化目标 P95 不超过 1 秒（不含网络异常重试）。
- 团队成员列表、Agent/Skill/Provider 列表和日志筛选必须分页，禁止一次加载全公司聊天正文。
- 同步队列支持批量上传、压缩和退避；单个坏事件不得阻塞后续事件。
- Agent 日志列表默认查询元数据，正文和 trace 采用按需加载。

### 5.3 安全与合规

- 所有服务端资源访问必须做组织作用域校验，前端隐藏不是安全边界。
- Provider 凭据、WhatsApp session、设备授权和记住登录凭据必须分开加密管理。
- 聊天正文、话术资料和模型输入输出按公司策略设置保留期和同步级别。
- 审计日志应包含 actor、scope、action、target、result、request ID、时间和客户端版本。
- 平台支持访问必须最小权限、临时授权、可撤销、过期和全程留痕。
- 不在日志、错误信息或前端响应中泄露 API Key、Cookie、密码、完整手机号或敏感消息正文。

### 5.4 可用性与容错

- 云端服务无状态部署，数据库迁移可重复执行，关键写入使用事务和幂等键。
- 本地离线时聊天基本功能可用；企业管理数据必须明确显示“未同步”。
- Agent Provider 超时、限流、非法 JSON 和网络中断必须可观测且可重试/降级。
- 同步、数据库迁移和 OTA 失败必须提供恢复路径，不允许静默覆盖本地数据库。

### 5.5 可观测性

- 每个登录、权限拒绝、同步、Agent run、Skill reference 命中、采纳、OTA 和支持访问都有 trace/request ID。
- 平台、公司、团队三级分别提供健康指标和错误聚合视图。
- 日志内容与聊天正文分离；默认使用结构化元数据，正文只在授权诊断链路中读取。

## 6. 现有版本兼容约束

企业版必须以当前代码为增量改造基础，不能假设已有完整多租户能力：

- 当前 `internal/auth` 仍以 `Role` 和用户权限为主，企业版需要增加组织成员关系与策略判定。
- 当前 `accounts`、`chats`、`messages`、`agent_runs`、`assistant_usage_logs` 和 `agent_skills` 缺少统一的公司/工作区/团队作用域。
- 当前桌面端本地 PostgreSQL 承担 WhatsApp 账号、会话和聊天数据，企业版需要引入同步 outbox，而不是直接把本地数据库改成远程数据库。
- 当前前端 `AuthContext`、`AppShell`、`App`、`AdminPage` 和 `ChatsPage` 没有统一工作区上下文，企业版需要先建立上下文，再迁移页面。
- 当前 Agent/Skill/JEV/Provider trace 已能记录基础运行信息，企业版需要扩展为组织作用域、版本、reference 和审计可查询结构。
- 当前 `admin@example.com` 只能作为平台初始超级管理员兼容入口，企业版正式模型必须依赖平台/公司/团队关系，不得用邮箱硬编码所有授权。

## 7. 发布与验收门槛

企业版 1.0.0 进入公开企业试用前，至少满足：

1. 公司、工作区、团队、成员和角色可以完整创建、邀请、停用和审计。
2. 公司管理员、团队管理员、普通成员和平台管理员的 API 越权测试全部通过。
3. 本地账号、聊天和消息可以按同步策略可靠进入云端，重复、断网、重试和乱序场景有测试。
4. 前端切换团队后没有跨团队缓存、列表、日志和草稿串数据。
5. Provider、Agent、Skill、reference 和模型目录的继承、覆盖、只读和停用规则可解释。
6. Agent 运行日志能证明 Provider、模型、决策/jev、Skill 和 reference 是否实际执行。
7. 公司可查看自己的成员数据，团队只能查看本团队，平台默认看不到客户正文。
8. OTA 包含签名、校验、备份、迁移失败恢复、灰度和回滚演练。
9. 企业版部署使用独立 Git 分支、Docker project、数据库卷、域名/端口和环境变量，不影响第一批用户主线。
10. 形成设计文档、任务拆解、API/数据库迁移清单、测试矩阵、上线 runbook 和回滚 runbook。

## 8. 术语约定

| 术语 | 定义 |
| --- | --- |
| Platform | 软件提供方的控制面，不等同于客户公司 |
| Organization | 一个客户公司租户，隔离成员、业务数据、配置和用量 |
| Workspace | 公司内的业务体系或工作区，可包含多个团队 |
| Team | 工作区内的团队，是成员、账号、聊天和配置的主要授权边界 |
| Scope | 资源所属层级：platform、organization、workspace、team |
| Capability | 当前上下文允许的具体操作能力，不等同于角色名称 |
| Data plane | 本地 WhatsApp 连接、会话、聊天和媒体处理链路 |
| Control plane | 云端组织、权限、配置、日志、统计、授权和 OTA 链路 |
| Sync outbox | 本地待上传事件队列，用于离线重试和幂等同步 |
| Reference | Skill 下可被检索和注入 Agent 上下文的客户话术/知识文档 |
